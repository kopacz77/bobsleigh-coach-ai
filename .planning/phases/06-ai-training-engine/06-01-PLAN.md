CREATE TABLE public.weekly_plans (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    athlete_id UUID NOT NULL REFERENCES public.athletes(id),
    coach_id UUID REFERENCES public.coaches(id),
    week_start DATE NOT NULL,
    week_end DATE NOT NULL,
    plan_data JSONB NOT NULL,
    training_phase TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending_review',
    approved_at TIMESTAMPTZ,
    approved_by UUID,
    rejected_at TIMESTAMPTZ,
    rejected_by UUID,
    rejection_notes TEXT,
    version INTEGER NOT NULL DEFAULT 1,
    parent_plan_id UUID REFERENCES public.weekly_plans(id),
    generation_metadata JSONB,
    injury_risk_score NUMERIC(4,3),
    injury_risk_factors JSONB,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE(athlete_id, week_start, version)
);

CREATE INDEX idx_plans_status ON public.weekly_plans(status, week_start);
CREATE INDEX idx_plans_athlete_week ON public.weekly_plans(athlete_id, week_start);

<task type="auto">
  <name>Task 3: Build plan generation service</name>
  <files>backend/app/services/plan_generation_service.py</files>
  <action>
Create PlanGenerationService -- the core rule-based plan generation engine. This is the most important file in Phase 6.

The service should implement:

1. `generate_plan(athlete_id: str, week_start: str) -> dict` main method that:
   - Fetches athlete profile from athletes table (training_level, training_frequency, performance_targets)
   - Gets current PMC state via PMCService (CTL, ATL, TSB)
   - Gets recent workouts (last 4 weeks) via Supabase query
   - Gets recent wellbeing data (last 7 days)
   - Gets coach feedback history (rejection_notes from past weekly_plans for this athlete)
   - Determines training phase (use athlete.performance_targets.training_phase if set, else default to "general_prep")
   - Selects weekly template based on phase (from 06-RESEARCH.md periodization model)
   - Fills template with exercises via ExerciseSelectionService
   - Assigns weights using history-first, profile-fallback, conservative-estimate logic
   - Produces plan_data JSONB matching the research schema
   - Saves to weekly_plans table with status "pending_review"
   - Returns the full plan dict

2. `generate_plans_batch(coach_id: str, week_start: str) -> List[dict]` that:
   - Gets all athlete_ids for the coach (via CoachService.get_athlete_ids)
   - Generates a plan for each athlete (catching per-athlete errors)
   - Returns list of generated plans

3. Internal helpers:
   - `_select_weekly_template(phase: str, tsb: float, frequency: int) -> List[dict]` -- returns 7-day template structure based on the bobsleigh periodization model from research
   - `_assign_weights(exercises: list, recent_workouts: list, athlete: dict) -> list` -- three-tier weight assignment (history -> profile max -> conservative estimate at 50-60% of related exercise)
   - `_apply_coach_preferences(plan_data: dict, feedback_history: list) -> dict` -- simple keyword matching on rejection notes (volume_high -> reduce sets, intensity_high -> reduce weight %)
   - `_round_to_plate(weight_kg: float) -> float` -- round to nearest 2.5kg

Key constraints from CONTEXT.md:
- Plan scope is always 7 days (Mon-Sun)
- Full prescription: exercises with sets, reps, weight_kg, intensity_percent
- Includes warm-up and cool-down for each session
- Never more than 3 consecutive training days
- High-intensity sessions need lower-intensity or rest day between them

Weekly templates (from research):
- general_prep: 4-5 sessions (Mon: Lower Strength, Tue: Speed, Wed: Upper/Recovery, Thu: Power, Fri: Speed Endurance, Sat: optional, Sun: rest)
- specific_prep: 4-5 sessions (Mon: Acceleration, Tue: Max Strength, Wed: Recovery, Thu: Power, Fri: Speed, Sat: Light/rest, Sun: rest)
- pre_competition: 3-4 sessions (Mon: Speed, Tue: Power Maintenance, Wed: Rest, Thu: Light technique, Fri-Sun: rest/comp)
- competition: 2-3 sessions (maintenance only)
- transition: 2-3 sessions (active recovery, general fitness)

Follow existing service patterns: class-based, async methods, get_supabase() for DB, PMCService for PMC data.
